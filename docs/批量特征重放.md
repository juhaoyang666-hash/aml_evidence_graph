# 批式 PIT 特征重放与大数据迁移说明

本项目的全量特征由单机 Python PIT 管线生成（约 950 万行、321 个日期分区），没有公司级
Hive 仓、Spark 资源队列或实时特征存储。本实验使用 DuckDB 和 Polars 只读重放一个代表性
窗口特征，并增加本地 Spark 五特征全量/增量重放，验证与官方 PIT 的语义一致性。

- 产物：`artifacts/batch_feature_replay/`
- 环境：`pip install ".[batch]"`（当前锁定 `duckdb 1.5.5`）
- 命令：`PYTHONPATH=src python scripts/data/run_batch_feature_replay.py`

## 当前批式数据组织

| 步骤 | 实现 |
|---|---|
| 输入 | `artifacts/prepared_transactions/event_date=*` 分区 Parquet |
| 变换 | 账户滚动窗口、关系窗口、图统计和规则命中 |
| 输出 | `artifacts/pit_features/event_date=*`、特征登记和 run manifest |
| 时间约束 | 每笔交易只读 `[t-window, t)`；同一时间戳交易相互不可见 |

等价的数仓处理结构：

```text
fact_transactions (partitioned by event_date)
  → daily account/pair aggregates
  → time-ordered rolling state by account_id/pair_id
  → explicit equality join back to transaction grain
  → partitioned PIT feature table
```

ODPS、Hive 或 Spark 实现应使用预聚合和显式等值连接，禁止普通笛卡尔积。

## 重放协议与结果

对 5 个 scored day 加 7 天历史窗口重放 `sender_outgoing_count_7d`，分别使用 DuckDB
`RANGE` window 和 Polars rolling，与官方 PIT 逐行对齐。

| 引擎 | Match rate vs PIT | 约 rows/s |
|---|---:|---:|
| DuckDB `RANGE` window | **1.0** | ~3.7e5 |
| Polars rolling | **1.0** | ~9.2e4 |

2026-07-31 在将 DuckDB 纳入正式 optional dependency 后补做 1 天运行时回归：
8,400 个 scored rows、10 个历史分区，DuckDB/Polars 的 match rate 均为 `1.0`，
平均绝对误差均为 `0.0`。当次本机吞吐约为 `125,176 / 71,119 rows/s`；
这是依赖与脚本运行时回归，不取代上表 5 天主协议，也不是性能 SLA。

## Spark 五特征等价（Windows 完整 950 万行）

> Windows 本地 Spark 完整数据重放，不是生产集群 SLA。命令：
> `scripts/data/replay_spark_features.py` + `scripts/data/evaluate_spark_equivalence.py`。
> 本次报告位于 `artifacts/spark_replay_fullscale/`，包含 JSON、Markdown 和资源曲线 CSV。

| 项 | 值 |
|---|---|
| 结果 | **通过** |
| 全量重放 | 扫描/输出 9,504,852/9,504,852 行，71.29 秒，峰值进程树内存 12,112.4 MB |
| 增量重放 | 扫描 885,238 行 30 天历史，输出 2023-08-23 的 8,400 行，16.39 秒，峰值 2,920.7 MB |
| Spark | 全量 `local[8]` / 增量 `local[4]`，shuffle partitions=64/32，physical Exchange=4 |
| 资源曲线 | 0.25 秒采样，全量/增量共 300 个样本；记录 RSS、累计 CPU time 和进程数 |
| 对齐 | `transaction_id` 显式等值连接；无普通笛卡尔积 |

| PIT 特征 | Match rate | 最大绝对误差 |
|---|---:|---:|
| sender_outgoing_count_1d | 1.000000 | 0 |
| sender_outgoing_count_7d | 1.000000 | 0 |
| sender_outgoing_count_30d | 1.000000 | 0 |
| receiver_incoming_count_7d | 1.000000 | 0 |
| relationship_count_7d | 1.000000 | 0 |

Windows 缺少 Hadoop native 写入组件，本机采用 Spark 计算后 Arrow driver 写出；
窗口聚合与 shuffle 由 Spark 执行。Linux/集群环境使用原生 Spark Parquet writer。
当前记录物理 Exchange 节点数，不宣称生产集群 shuffle bytes。
该结果已覆盖完整 9,504,852 行，但仍只验证 5 个代表性历史计数特征，
不替代包含全部特征族的官方 PIT 流水线。早期 355,998 行 smoke 数字仅保留为开发阶段记录。

## 已验证的重建优化

初版单进程全量 PIT 构建约需 8 小时。规则阈值只依赖已有 PIT 列，因此规则版本更新不需要
重放历史窗口；`scripts/data/backfill_rule_hits.py` 可以直接补写命中列和规则证据。

| 方式 | 实测耗时 |
|---|---:|
| 全量 PIT 重建 | 约 8 小时 |
| 规则回填 dry run | 约 47 秒 |
| 规则回填并写入 | 约 2 分钟 |

脚本在规则引用特征缺失时拒绝执行，避免把真正需要历史重放的特征变更误当作简单回填。
后续若继续扩大数据规模，优先考虑增量窗口累加器、按账户哈希分桶并行和向量化窗口；任何
替换实现都必须重新验证 PIT 与同秒隔离语义。

## 如何用于面试

- 已实现：千万级分区 Parquet、严格时间窗口、特征登记、运行清单、DuckDB/Polars 重放，
  以及本地 Spark 五特征全量/增量等价验证。
- 未实现：公司级 Hive/Spark 集群作业、资源队列、在线特征存储或生产 SLA。
- 可迁移部分：PIT 时间语义、日期分区、账户/关系 key、增量状态和回写交易粒度。
- 仍需重验：迟到数据、跨环境分区回补、集群 shuffle 字节、故障重试与原生 writer 性能。

## 边界

该实验仍不替换官方 Python PIT，也不能表述为已完成 Spark/Hive 生产迁移。它证明三类批式
实现可在各自受控样本上复现同一时间协议；Windows 的 Spark 写出是 Arrow driver fallback，
不是集群分布式写入证据。
