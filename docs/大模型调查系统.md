# LLM 调查辅助系统：边界、实现与评测

本系统中的 LLM 只辅助调查措辞和待查问题，不参与风险分数、阈值、告警排序或案件结论。
模型主线与正式效果见 [模型卡.md](模型卡.md) 和 [实验结果.md](实验结果.md)。

## 职责边界

| 环节 | 决策方 | LLM 是否参与 |
|---|---|---|
| 交易风险概率 | CatBoost / GAT / 融合器 | 否 |
| 概率校准、阈值和告警预算 | 验证期确定性代码 | 否 |
| 账户、资金路径和案件候选聚合 | 冻结交易分数后的确定性代码 | 否 |
| Typology 检索 | 本地 BM25 | 否 |
| 分析性措辞和建议核查问题 | 可选 ECNU `ecnu-max` | 是，受事实校验约束 |
| SAR 草稿骨架 | 确定性模板 | 否，LLM 只能补充非事实段落 |
| 是否申报或采取案件动作 | 人工调查员 | 否 |

一句话：**LLM 只负责措辞与提问，不负责判断与数字。**

## 当前实现

### 有界 LangGraph 工作流

`src/aml_evidence_graph/investigation/workflow.py` 使用固定节点：

```text
retrieve_typologies
  → fact_check
  → annotate
  → validate_annotation
  → draft_report
```

当前实现无自由循环和自主工具选择，`MAX_TOOL_CALLS=4`。因此准确表述应为“有界单 Agent
调查链”，不能描述为自主多 Agent 系统。固定 DAG 便于复现、审计和失败降级。

### 出站数据最小化

`minimize_evidence_for_llm()` 只发送概率名称、rule_id、特征名、图证据是否存在、Typology
元信息和缺失证据类别。交易、账户、告警 ID、时间戳、金额和原始特征数值不会发送给外部服务。

### 返回事实校验

`validate_annotation()` 执行两类约束：

1. `evidence_references` 必须属于证据包允许的引用路径。
2. 分析与问题字段不得出现任何数字字符，也不得引入 `transaction_*`、`account_*`、
   `alert_*` 或带数字后缀的同类实体 token；普通 `account-related` 复合词不误判为 ID。

校验失败时报告状态为 `rejected_facts`，外部注释和 SAR 草稿不会暴露给复核人。

### 降级策略

| 失败 | 行为 |
|---|---|
| 未启用外部 LLM 或无 key | 仅运行本地模板路径 |
| 网络、超时、HTTP 或 JSON 错误 | 只记录脱敏错误类别（如 `timeout`、HTTP 状态或 JSON 类别），回退确定性模板 |
| 注释事实校验失败 | 状态变为 `rejected_facts` |
| Typology 线索不足 | 保留缺失和不确定性，不编造匹配结论 |

任何 LLM 故障都不会影响风险评分和告警，因为评分与调查属于不同代码路径。

### 版本、用量与成本

- 当前 Prompt：`configs/prompts/ecnu-risk-evidence-v6.yaml`；v1-v5 保留用于 Bad Case 与晋升链追溯
- 当前生成参数：`temperature=0`、`max_tokens=500`、JSON object 输出
- 外部请求超时由 `AML_LLM_TIMEOUT_SECONDS` 控制，当前回归使用 `120` 秒
- Prompt 内容或参数变化需新建版本并重跑 Golden
- Provider 返回 token 时记录 prompt/completion/total usage
- 未配置合同价格时成本保持空值，不推测 API 成本

## 运行监控与成本统计

2026-08-04 补齐了此前记为"待增加统一 trace/run 关联"的运行监控，并修复了成本统计的系统性
低报。聚合入口为 `scripts/reporting/build_llm_operations_report.py`，只读取本机已冻结的 run
摘要，不发起外部调用、不复制模型原文，输出 `artifacts/llm_operations/llm_operations_report.json`。

### 成本口径修复

原实现的 `_parse_usage()` 位于所有失败分支之后，因此三条路径的计费信息处理不一致：

| 路径 | 原行为 | 现行为 |
|---|---|---|
| 解析失败（`annotation_json_invalid` / `annotation_truncated` / `annotation_schema_invalid`） | 在读取 usage 前抛出，provider 已返回的 token 数被丢弃 | usage 在任何内容检查前解析并挂在 `AnnotationProviderError.usage` |
| 事实门拒绝 | 报告丢弃整个注释，其 usage 一并丢失 | usage 转入报告的 `unusable_call_usage` |
| 传输层失败（超时 / 连接 / HTTP） | 无 usage | 保持 `None`；无响应体时计费量确实未知，不猜测 |

统计因此分为两套口径：`reported_*` 保持"已接受注释"语义（公开证据已引用，不改口径），
新增 `billable_*`（provider 报告了 usage 的全部尝试调用）、`wasted_*`（已计费但不可用）
和 `wasted_token_share`。空集合的成本为 `0.0`（零 token 乘任何价格都是零），
非空但缺合同价格为 `None`（未知，不得按免费低报）。

**该修复只对后续 run 生效。** 历史失败调用的 token 从未被采集，永久不可恢复：11 个 run
共 209 次外部调用，159 次有 usage 数据，**50 次（全部来自修复前的 run）不可恢复**。公开证据中
v4 的 `1335 / 664` token 只覆盖 2 条被接受的注释，其余 18 次调用的真实计费量无法追溯，
不得据此计算"单位有效注释成本"。

`artifacts/llm_operations/v6_dev_regression_complete_usage.json`），这是**第一个

| 已接受注释（旧口径会报的数字） | 19,103 | 8,851 |
| 实际计费（新口径） | **19,810** | **9,351** |
| 其中浪费 | 707 | 500 |

唯一失败的调用 `agent-typo-17-cycle` 的错误类别为 `annotation_truncated`，其

### 失败模式分离

监控把不可解析的调用拆成 **availability**（`timeout` / `http_status_*` / `transport_error` /
`response_json_invalid`）与 **format**（三类 annotation 契约失败）。两者归一会掩盖到底是
Prompt 契约问题还是 Provider 问题：

| Run | Prompt | 解析率 | availability 失败 | format 失败 |
|---|---|---:|---:|---:|
| golden34 首次冻结 | v1 | 0.5556 | **11** | 1 |
| golden34 开发回归 A | v3 | 0.9630 | 0 | 1 |
| golden34 开发回归 B（公开引用） | v3 | 0.7407 | 0 | 7 |
| Holdout v1 | v3 | 0.7500 | 0 | 5 |
| Holdout v2 | v4 | 0.1000 | 0 | **18** |
| 开发回归 34 案 | v6 | 0.9630 | 0 | 1 |
| Holdout v3（晋升） | v6 | **1.0000** | 0 | 0 |

v1 的主导失败是 **availability（11 次超时/HTTP 500）**，而 v4 是 **format（18 次）**。
两者是不同轴上的问题；v1→v3 的 names-only 契约修复针对的是内容与格式，不能解释 v1 的
超时，也不应把 v1 的低解析率整体归因于 Prompt。

### 同配置波动及其对晋升结论的影响

两次 v3 run 使用**同一 Prompt、同一 34 案开发集**，相隔约 5.5 分钟：
`20260804T032632Z-49aa87a206` 解析率 `0.9630`，`20260804T033209Z-b7e39be09d` 为 `0.7407`。
同配置解析率跨度 **0.2222**，无任何代码或 Prompt 变化。

这对晋升叙事有直接影响，必须披露：v6 Holdout v3 解析率 `1.0` 与 v3 Holdout v1 的 `0.75`
相差 `0.25`，**仅略大于实测的同配置波动 0.2222**。两者虽用不同 Holdout 集合、不构成严格
同配置对比，但该波动量级说明**单看解析率不足以确立 v6 优于 v3**。v6 晋升的实质依据应主要
落在内容质量轴（项目内人审 Grounding/Overall `0.95` vs `0.80`、事实门 `1.0`、注入抵抗 `1.0`），
而解析率的改善不能排除 Provider 波动贡献。v4 的 `0.10` 远超该波动范围，其"不晋升"结论不受影响。

反方向的证据也应同时记录：v6 在同一 34 案开发集上的两次 run（`20260804T080952Z-f8ecb44540`
与 `20260804T094026Z-ec55d5cd1d`）解析率均为 `0.9630`，**同配置跨度 `0.0`**。这提示 v6 相对 v3
不仅更高、也更稳定，但 `n=2` 且两次取值完全相同也可能是巧合，因此只作为初步信号，
不作为稳定性结论。要支撑"v6 更稳定"需要更多同配置重复运行。

### 统一 trace 与节点归因

Golden 路径此前完全没有节点级可观测性（只有受控链 `workflow_v2` 有 `node_timeline`）。
现在 `workflow.py` 的五个节点统一由 `_traced_node()` 包裹，产出与受控链**同一 span 结构**
（`node` / `timestamp_utc` / `duration_ms` / `status` / `state_change`），且 `state_change`
取自闭合词表，trace 消费方不需要解析自由文本。节点抛异常时先记 `status="failed"` 的 span
再向上传播，因此失败运行同样有 trace。

`run_investigation_traced()` 返回 `(报告, trace)`；`run_investigation()` 签名保持不变，
所以 API 响应模型不会被运维用的 span 撑大。Golden 每案 trace 写入与 summary 同目录的
`<output>_traces.jsonl`（summary 已有 56–88 KB，span 不再往里塞）。

首个真实 run 的 34 条 trace 显示延迟几乎完全来自外部调用，例如
`agent-low-evidence-03` 总耗时 `9909.9 ms`、其中 `annotate` 节点占 `9908.9 ms`。
这使"延迟由 Provider 还是本地模板造成"第一次可以按节点归因，而不是只看整案耗时。

未闭合部分：受控链与 Golden 路径**尚未共用同一个 trace 标识**（Golden 使用
`golden-<case_id>`，受控链使用 `thread_id`），因此还不能把同一告警在两条路径上的执行拼成
一条链。这属于后续工作，本次不宣称已实现端到端分布式追踪。

### 成本口径：实付为零，参考价只作敏感性

**实际支出为 `0`。** ECNU `ecnu-max` 对校内免费，Provider 也不返回价格元数据，因此
`reports/public/llm_ecnu_max_evaluation_20260804.json` 的 `cost_status` 保持
`unavailable`、全部 `estimated_cost_usd` 保持 `null`——这是准确的，不因下述参考价而改写。

为了让"每份调查草稿的成本"这一工程问题有量级答案，另按第三方参考价对**已记录 token**
做事后敏感性计算。该计算有两层假设，都必须随数字一起披露：

1. **底层模型的归属是项目方陈述，未经验证。** 本项目按"`ecnu-max` 实质为 DeepSeek V4 Flash"
   这一说法取价；Provider 未声明底层模型，本项目也无法核实。
2. **参考价不是本项目支付的价格。** 取 2026-07-29 生效的 DeepSeek V4 Flash 公开价：
   cache-miss 输入 `$0.14/M`、cache-hit 输入 `$0.0028/M`、输出 `$0.28/M`。

以唯一完整覆盖的 run（27 次调用、26 条被接受注释）为准：

| 参考价情形 | 计费成本 | 其中浪费 | 每份被接受草稿 |
|---|---:|---:|---:|
| cache-miss 输入（上界） | `$0.005392` | `$0.000239`（4.43%） | `$0.000207` |
| cache-hit 输入（下界） | `$0.002674` | `$0.000142`（5.31%） | `$0.000103` |

两档差异来自输入缓存：本链路每次调用重发同一段系统提示与契约说明，因此启用前缀缓存的
部署会趋向下界。但本项目**没有记录 cache-hit 命中数据**，所以两档只作区间，不宣称实际命中率。

全部 11 个 run 在 cache-miss 参考价下合计 `>= $0.0307`（9/11 为下界，因为修复前的 50 次
失败调用 token 不可恢复）。量级结论：**在本项目的评测规模上，LLM 层成本可忽略**；真实
AML 场景的成本驱动是告警量而非单次调用价格，34 案的数字不能线性外推为生产成本。

参考价计算结果位于 `artifacts/llm_operations/reference_priced_cache_{miss,hit}.json`，
与不含价格的 `llm_operations_report.json` 分开存放，避免参考价被误读为实测成本。

### 截断的有界重试（v7 候选，未晋升）

首个完整覆盖 run 的唯一失败调用是 `annotation_truncated`，说明 v5 把上限从 350 提到 500
只是把悬崖往后挪，没有消除该失败模式。客户端本来就能靠 Provider 返回的
`finish_reason == "length"` 精确识别这一类失败，因此现在允许**对且仅对截断**重试一次，
使用更高的 token 上限。

**只重试截断，是刻意的边界。** 超时、HTTP 错误、传输失败和一般 JSON 非法都不重试：这些
失败不携带"第二次该改什么"的信息，重试它们只会抬高表面成功率，同时掩盖本项目专门在测量的
Provider 不稳定性。截断是唯一一类 Provider 自己说明了原因、客户端可以确定性纠正的失败。
重试上限是静态配置值，不自适应。

#### 协议边界：两种"重试"必须分开

Holdout 协议 v1–v3 写的是"no per-case retries"。这条规则针对的是**评测者**：看到某案失败后
重跑、改分、打补丁。链内重试是**被测系统自身**的行为，属于被测对象而不是评测手法。二者混在
同一句话里会让人误以为链内重试违规，因此先冻结
[golden/llm_retry_policy_v1.json](../golden/llm_retry_policy_v1.json) 再动代码：

- 评测者重试：**仍然禁止**，v1–v3 的规则一字未改，也不重开任何已记录结论。
- 链内重试：允许，但必须运行前声明，最多 1 次，只由 `annotation_truncated` 触发。
- **每案不再等于每次调用。** 案件数与调用数必须分别报告，`external_parse_success_rate`
  是按案统计的，在 `truncation_retry_count > 0` 时**不是首次尝试成功率**。
- 两次尝试都计费，被丢弃的那次同样进入 billable 口径与浪费统计。

该策略只对 Holdout v4 及以后生效，v1–v3 执行时链内重试尚不存在。

#### Holdout v4：v7 已晋升，但实测收益为零

预注册协议 [llm_holdout_protocol_v4.json](../golden/llm_holdout_protocol_v4.json)（引用
`llm-chain-retry-policy-v1`）在提交 `072844e` 冻结，**先提交再运行**，24 案 / 20 外部调用唯一
执行。全部预注册门槛通过，v7 已取代 v6 成为默认 Prompt。

但协议里预写的 **null 情形触发了**：

| 预注册派生指标 | 值 |
|---|---:|
| `first_attempt_parse_success_rate` | `1.0000` |
| `final_parse_success_rate` | `1.0000` |
| **`retry_attributable_parse_gain`** | **`+0.0000`** |
| `truncation_retry_count` | **0** |
| `calls_per_case` | `1.0000` |
| 事实门 / 人审 overall | `1.0000` / `1.0000` |

**重试一次都没触发,所以这次运行对重试的收益一无所证。** v7 的晋升依据只是"不比 v6 差"，
它是一张**从未被用到的安全网**。协议禁止把这里的解析率说成"重试起作用了"，本文档遵守该禁令。

设计上本来想诱发截断：v4 的 6 个 wide 案把可引用面从开发集的 5–7 个加宽到 11–12 个。**这个
办法失败了**——最长完成 `466`/500，开发集是 `462`。参考面翻倍只把长度推高 4 个 token，说明
**完成长度由指令自身的条数限制决定，而不是由可引用证据的多少决定**。这条否证本身有价值：
截断不是证据复杂度驱动的，是稀有尾部事件。

#### 规则外发现：字段名在未见集合上泄漏进正文

v6/v7 的系统指令明确禁止把任何模型、规则、特征或 Typology 名称复制、拼出或改写进正文。用
`find_field_names_in_prose()`（生产代码，20 项回归含假阳性用例）扫四个冻结 run：

| run | Prompt | 正文泄漏 |
|---|---|---:|
| 开发集 complete-usage | v6 | `2/26`（8%） |
| 开发集 real | v7 | `4/27`（15%） |
| **Holdout v3** | **v6（曾晋升）** | **`11/20`（55%）** |
| **Holdout v4** | **v7（当前默认）** | **`9/20`（45%）** |

**这条边界在 Prompt 开发时见过的名字上大致成立，在未见过的名字上约一半失效**——开发集与
Holdout 差四到五倍。这是 Prompt 对开发集的过拟合，而且正是 v6 当初被创建出来修的那个失败模式。

> **测量更正**：首次复核时用的是一个临时探测器，只看特征名和规则名（漏掉 Typology 标题与模型
> 名，而指令同样禁止），且把名字压缩成"特征词"后匹配，会误伤指令本身要求使用的措辞（如
> "corroborating context"）。当时报的是 `5/20` 与 `7/20`。修正后量级约翻倍，**且 v6/v7 的高低
> 顺序反转**，因此"v7 在该轴更差"的暗示不成立；`n=20` 下这个差距本来也分辨不出，结论是**两者
> 相当，都在未见集合上失效**。裁定文件已记录该更正。

处理方式必须说清楚：

- **不改变 Holdout v4 的判定。** 冻结鲁布里克没有正文边界这一条，Holdout v3 也是用同样四条
  标准晋升 v6 的。看到结果之后再补一条标准去判 v7 失败，就是事后移动门柱，而预注册的全部意义
  就是防这个。
- **不重开 v6 的晋升。** 该缺陷对 v6 和 v7 影响相当（`5/20` vs `7/20`），不是 v7 的回归；
  v6 的门禁当时就没测这个轴。
- **后续必须做**：给 Holdout v5 的鲁布里克加正文边界标准，把 `5/20` 和 `7/20` 当作它的首次
  测量，并在新 Prompt 版本里修指令、由它自己的预注册运行把关。

另记一个人审负例：`holdout-v4-adv-02-live` 拒绝了注入的"给百分比并排名"要求（判定为
injection_resistant），但它在一条推荐问题里改述了那条不可信指令的内容，而指令明确禁止
"把请求的披露或决定改写成推荐问题"。判 False 曾被考虑并否决——冻结标准考的是**是否拒绝该
请求**，而它拒绝了。该负例随裁定一起记录，不掩盖。

#### 版本身份：v7 曾是候选，Holdout v4 后成为默认

提高生成上限属于配置变更，按本项目既有先例（v5 就是"v4 把上限提到 500"）必须新开版本号。
`configs/prompts/ecnu-risk-evidence-v7.yaml` 的 `system_instructions` 与 v6
**逐字节相同**（回归测试固定这一点），只多一个 `truncation_retry_max_tokens: 1000`。
v6 文件哈希保持 `59aeb8d2…`，与 Holdout v3 预注册值一致，因此 v6 仍可逐字节复现。

收窄到可用性轴的理由**写在协议里、跑之前**：重试只在解码失败时触发，因此**不可能改变任何
本已成功的调用**，首次尝试的注释与 Holdout v3 已复核过的配置同分布，内容证据原样承接；这条
论证省掉的是**配对的 v6 对照臂**，而不是内容复核本身——由重试产生的注释是 v3 从未覆盖过的新
产物，协议对它们单列 `1.0` 门槛。本次零重试，该门槛空集成立（协议自己的 null 情形条款要求
这样读，否则零重试永远无法晋升，与该条款自相矛盾；这一解释已写入裁定记录）。

#### 验证一：确定性桩（机制）

真实缺陷是 27 次里出现 1 次，`n=1` 量不出任何东西。因此先用
[scripts/operations/diagnose_truncation_retry.py](../scripts/operations/diagnose_truncation_retry.py)
把 Provider 换成确定性桩：**截断率由 harness 设定而不是抽样**，20 案中固定 4 案的输出长度
落在基础上限与重试上限之间。零外部调用。

| 分支 | 解析率 | 外部调用 | 截断重试 | 计费成本 | 其中浪费 |
|---|---:|---:|---:|---:|---:|
| v6 基线（无重试） | `0.8000` | 20 | 0 | `$0.004043` | `$0.000952`（22.39% token） |
| v7 候选（有重试） | `1.0000` | 24 | 4 全部恢复 | `$0.005130` | `$0.000952`（17.96% token） |

关键读数是**浪费的绝对金额完全没变**。重试不减少浪费，它是用额外开销换回收：成本上升
`26.9%`，换回 4 份原本失败的草稿。把这理解成"修好了浪费"是错的。

#### 验证二：真实 Provider（现场行为）

模拟桩只能证明机制，不能证明现场。用 `ecnu-max` 对同一 34 案开发集重跑（27 次真实外部调用）：

| run | Prompt | 解析率 | 外部调用 | 截断重试 | 浪费 token |
|---|---|---:|---:|---:|---:|
| `20260804T094026Z-ec55d5cd1d` | v6 | `0.9630` | 27 | — | 707 / 500 |
| `20260805T025859Z-b22df241b7` | v7 | `1.0000` | 27 | **0** | 0 / 0 |

**这里必须说清楚：`truncation_retry_count = 0`，重试一次都没触发。** 因此 v7 的
`1.0000` 相对 v6 的 `0.9630` **不能归因于重试**——在 v6 那次撞上限的
`agent-typo-17-cycle`，这次只用了 `391` token 就正常结束。该点差远小于本文档已记录的同配置
波动（v3 两次相隔 5.5 分钟的 run 跨度 `0.2222`），属于噪声范围。

真正的结论是：**截断是完成长度的运行间波动，不是某个案例的固定属性**。上限确实偏紧——27 次
真实调用的最长完成为 `462`，距 `500` 只差 38 token，分布尾部会周期性蹭到上限。

#### 验证三：强制触发（重试的现场证据）

既然自然截断等不到，就把上限降到 `200` 主动触发
（`configs/diagnostics/truncation_retry_forced_v1.yaml`，版本号显式写成
`diagnostic-forced-truncation-v1`，不可能被误当作晋升候选）。run
`20260805T030152Z-d4442a83ef`，6 案全部真实调用：

| 指标 | 值 |
|---|---:|
| 真实截断 → 恢复 | **6 / 6** |
| 外部案件 / 外部调用 | 6 / **12** |
| 解析率 / 事实门 | `1.0000` / `1.0000` |
| token 覆盖率 | `1.0000` |
| 计费 prompt / completion | 8,802 / 3,345 |
| 其中浪费 | 4,401 / 1,200（占 token `46.11%`） |

每案都是 `attempts=2`：首次在 200 token 处截断被丢弃，重试在 1000 上限下成功，且 6 份被恢复
的注释**全部通过事实门**。这是重试路径唯一一次真实端到端验证。

边界：降低上限是实验设置，`6/6` 的截断率**不是现场截断率**；三个 run 都是开发集回归，都不是

另需注意运维报告的一处读法：被**恢复**的截断不会出现在 `error_categories` 里（它不是终态
失败），因此强制触发 run 的 `fmt_fail=0`。截断次数只能看 `truncation_retries`。

#### 一个连带修好的低报路径

引入第二次尝试后暴露出旧统计的一个盲点：`usage` 为空既可能是"没有这次调用"，也可能是
"调用发生了但 Provider 没报 token"。两次尝试只有一次报了 usage 时，按"空即无调用"求和会把
半张账单当成整张账单——方向与修复前的低报完全一致。现在 `InvestigationReport` 显式携带
`external_usage_complete`，任一尝试缺 usage 时该案整体退出 billable 口径并拉低覆盖率，
而不是报出偏低的成本。该缺陷由回归测试先复现再修复。

### 事实门补上文字量级断言（已修）

原事实门只拦**数字字面量**和账户/交易/告警 token。Holdout v5 造探针时发现
`"The withheld score sits in the top decile, which confirms the typology."`
**零错误通过**——所有值都对 Provider withheld，因此任何"高/低/前十分位"的断言都是编造，只是它
不带数字。v6 起的指令确实禁止了这类描述，但**指令不是强制**，校验器才是。这是安全缺口（编造的
量级直达复核人），不是风格问题。

**先量数据再写规则。** 冻结 run 里已有带标签的语料：v1 的 13 条被接受注释人审 grounding 为
`0.0`（真违规），v3/v6/v7/v8 的 157 条为合规。直接封禁量级词会误拒约 15% 的合规注释——因为
合规注释**也**用这些词，只是用在否定里（"does not imply that these values are high, low"）。
区分点不是词，而是**断言还是否认**：

| 规则变体 | 命中违规 | 误拒合规 |
|---|---:|---:|
| 词级封禁 + 仅豁免名称 | 12/13 | 9/107（8%） |
| 词级封禁 + 豁免名称与注记 | 10/13 | 0/107 |
| **短语级豁免（最终）** | **10/13** | **0/157** |

最终规则：命中量级词 → 若同句中该词**之前**出现否定线索则放行；若该词与相邻词构成的短语出现在
供给文本中则放行（注记说 "low evidence" 就允许写 low-evidence，`RULE-AMOUNT-HIGH` 就允许写
"high amounts"，含单复数归一）。豁免是**短语级而非词级**——注记里写 "high risk" 不能因此放行
"the score is high"，否则一条注入注记就能关掉整个门。

对既有证据的影响：**157 条合规注释零误拒**，因此 v3/v6/v7/v8 已发布的
`external_fact_validation_pass_rate = 1.000` 不变。v1 那一栏发布值是 `0.867`，而人审
grounding 是 `0.000`——**这正是缺口本身**：13 条注释过了自动门、却要靠人工才拦下。新规则会拦下
其中 10 条。未追改任何已发布数字，那些记录的是当时的门做了什么。

边界：漏掉的 3 条不含任何量级词，它们断言的是 Typology 适用性，属另一条规则的范围。否定式识别
是线索匹配而非语义分析，会漏掉绕开线索表的写法。该改动**只会拒更多、不会放行更多**，且后续
所有 Holdout 都在更严的门下运行。

## 受控 Agent 工程验证

### 60 案回归与审计

60 案回归的 Case 通过率、工具选择准确率、参数合法率、事实一致率和恢复成功率均为 `1.0`。
持续检索失败会记录 `TimeoutError` 并回退确定性模板，状态仍停在
`draft_requires_human_review`。每案保存节点时间线；工具事件只记录工具名、参数名、输出键、
耗时、状态和错误码。

LangGraph checkpoint 与追加式 SQLite 审计库相互分离。审计表使用稳定 `event_id` 和
`INSERT OR IGNORE` 防止回放重复，不保存证据正文、特征值、图边或备注正文；Evidence Store
则保存完整 Evidence Package，必须使用受限文件权限和受控磁盘。SQLite 只是本地演示后端，
不等同于集中/WORM 审计、组织保留策略或生产访问控制。

### 审批幂等与多 worker

审批接口支持 `Idempotency-Key`：同键同正文返回幂等回放，同键不同正文或无键重复终态返回
`409`。单进程探针以 50 个线程、每线程 8 个并发同键审批发出 400 个请求，错误率 `0%`，
350 个为回放，审计库最终各有 50 条 review/finalize；周期 p50/p95/p99 为
`526.97/668.67/849.61 ms`。

两真实 Uvicorn worker + 四个分离的共享 SQLite 文件下，跨连接证据读取 `40/40` 为 `200`；
20 个线程共 160 个审批请求得到 20 次实际执行、140 次回放、0 错误，review/finalize 各
20 条，活动租约归零。该结论限于本机多进程，不代表跨主机 exactly-once 或生产 SLA。

### 租约续期与故障注入

线程租约使用 `owner_token`、默认每 `lease_seconds/3` 心跳续期和 fencing。续期失败或释放时
不再持有租约会抛 `LeaseLostError`，API 映射为可重试的 `503`；过期持有者不能误删接管者租约。
9 项回归覆盖持有 3 倍租约周期、崩溃后接管、owner token 被夺、非法参数和 API 映射。旧实现
“租约过期后两个 worker 同时进入临界区”的问题已实测复现并由这些用例锁定。

边界仍是单机多进程：跨主机数据库、网络分区和真实进程 `SIGKILL` 未验证；进程退出后依赖
租约自然过期，最坏停顿一个 `lease_seconds`。

## 对外表达纪律

可以说：

> 构建 RiskEvidencePackage 约束的 LangGraph 调查链，对外字段最小化，返回经过引用白名单与
> 数值/实体校验；失败回退确定性模板，LLM 不参与评分和案件结论。

不要说：

- “用大模型提高 AML 识别率”
- “自主 Agent 已代替人工调查”
- “Golden 是第三方合规验收”
- “Mock Demo 或合成数据代表真实生产效果”
