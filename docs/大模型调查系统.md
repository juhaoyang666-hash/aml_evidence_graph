# LLM 调查辅助系统：边界、实现与评测

本系统中的 LLM 只辅助调查措辞和待查问题，不参与风险分数、阈值、告警排序或案件结论。
模型主线与正式效果见 [模型卡.md](模型卡.md) 和 [实验结果.md](实验结果.md)。

## 职责边界

| 环节 | 决策方 | LLM 是否参与 |
|---|---|---|
| 交易风险概率 | CatBoost / GAT / 融合器 | 否 |
| 概率校准、阈值和告警预算 | 验证期确定性代码 | 否 |
| 账户、资金路径和案件候选聚合 | 冻结交易分数后的确定性代码 | 否 |
| Typology 检索 | 本地 BM25 | 否 |
| 分析性措辞和建议核查问题 | 可选 ECNU `ecnu-max` | 是，受事实校验约束 |
| SAR 草稿骨架 | 确定性模板 | 否，LLM 只能补充非事实段落 |
| 是否申报或采取案件动作 | 人工调查员 | 否 |

一句话：**LLM 只负责措辞与提问，不负责判断与数字。**

## 当前实现

### 有界 LangGraph 工作流

`src/aml_evidence_graph/investigation/workflow.py` 使用固定节点：

```text
retrieve_typologies
  → fact_check
  → annotate
  → validate_annotation
  → draft_report
```

当前实现无自由循环和自主工具选择，`MAX_TOOL_CALLS=4`。因此准确表述应为“有界单 Agent
调查链”，不能描述为自主多 Agent 系统。固定 DAG 便于复现、审计和失败降级。

### 出站数据最小化

`minimize_evidence_for_llm()` 只发送概率名称、rule_id、特征名、图证据是否存在、Typology
元信息和缺失证据类别。交易、账户、告警 ID、时间戳、金额和原始特征数值不会发送给外部服务。

### 返回事实校验

`validate_annotation()` 执行两类约束：

1. `evidence_references` 必须属于证据包允许的引用路径。
2. 分析与问题字段不得出现任何数字字符，也不得引入 `transaction_*`、`account_*`、
   `alert_*` 或带数字后缀的同类实体 token；普通 `account-related` 复合词不误判为 ID。

校验失败时报告状态为 `rejected_facts`，外部注释和 SAR 草稿不会暴露给复核人。

### 降级策略

| 失败 | 行为 |
|---|---|
| 未启用外部 LLM 或无 key | 仅运行本地模板路径 |
| 网络、超时、HTTP 或 JSON 错误 | 只记录脱敏错误类别（如 `timeout`、HTTP 状态或 JSON 类别），回退确定性模板 |
| 注释事实校验失败 | 状态变为 `rejected_facts` |
| Typology 线索不足 | 保留缺失和不确定性，不编造匹配结论 |

任何 LLM 故障都不会影响风险评分和告警，因为评分与调查属于不同代码路径。

### 版本、用量与成本

- 当前 Prompt：`configs/prompts/ecnu-risk-evidence-v6.yaml`；v1-v5 保留用于 Bad Case 与晋升链追溯
- 当前生成参数：`temperature=0`、`max_tokens=500`、JSON object 输出
- 外部请求超时由 `AML_LLM_TIMEOUT_SECONDS` 控制，当前回归使用 `120` 秒
- Prompt 内容或参数变化需新建版本并重跑 Golden
- Provider 返回 token 时记录 prompt/completion/total usage
- 未配置合同价格时成本保持空值，不推测 API 成本

## 运行监控与成本统计

2026-08-04 补齐了此前记为"待增加统一 trace/run 关联"的运行监控，并修复了成本统计的系统性
低报。聚合入口为 `scripts/reporting/build_llm_operations_report.py`，只读取本机已冻结的 run
摘要，不发起外部调用、不复制模型原文，输出 `artifacts/llm_operations/llm_operations_report.json`。

### 成本口径修复

原实现的 `_parse_usage()` 位于所有失败分支之后，因此三条路径的计费信息处理不一致：

| 路径 | 原行为 | 现行为 |
|---|---|---|
| 解析失败（`annotation_json_invalid` / `annotation_truncated` / `annotation_schema_invalid`） | 在读取 usage 前抛出，provider 已返回的 token 数被丢弃 | usage 在任何内容检查前解析并挂在 `AnnotationProviderError.usage` |
| 事实门拒绝 | 报告丢弃整个注释，其 usage 一并丢失 | usage 转入报告的 `unusable_call_usage` |
| 传输层失败（超时 / 连接 / HTTP） | 无 usage | 保持 `None`；无响应体时计费量确实未知，不猜测 |

统计因此分为两套口径：`reported_*` 保持"已接受注释"语义（公开证据已引用，不改口径），
新增 `billable_*`（provider 报告了 usage 的全部尝试调用）、`wasted_*`（已计费但不可用）
和 `wasted_token_share`。空集合的成本为 `0.0`（零 token 乘任何价格都是零），
非空但缺合同价格为 `None`（未知，不得按免费低报）。

**该修复只对后续 run 生效。** 历史失败调用的 token 从未被采集，永久不可恢复：11 个 run
共 209 次外部调用，159 次有 usage 数据，**50 次（全部来自修复前的 run）不可恢复**。公开证据中
v4 的 `1335 / 664` token 只覆盖 2 条被接受的注释，其余 18 次调用的真实计费量无法追溯，
不得据此计算"单位有效注释成本"。

`artifacts/llm_operations/v6_dev_regression_complete_usage.json`），这是**第一个

| 已接受注释（旧口径会报的数字） | 19,103 | 8,851 |
| 实际计费（新口径） | **19,810** | **9,351** |
| 其中浪费 | 707 | 500 |

唯一失败的调用 `agent-typo-17-cycle` 的错误类别为 `annotation_truncated`，其
`prompt_tokens` 为 `None` 而 `billable_prompt_tokens` 为 `707`——这正是旧实现会静默丢弃的部分。

### 失败模式分离

监控把不可解析的调用拆成 **availability**（`timeout` / `http_status_*` / `transport_error` /
`response_json_invalid`）与 **format**（三类 annotation 契约失败）。两者归一会掩盖到底是
Prompt 契约问题还是 Provider 问题：

| Run | Prompt | 解析率 | availability 失败 | format 失败 |
|---|---|---:|---:|---:|
| golden34 首次冻结 | v1 | 0.5556 | **11** | 1 |
| golden34 开发回归 A | v3 | 0.9630 | 0 | 1 |
| golden34 开发回归 B（公开引用） | v3 | 0.7407 | 0 | 7 |
| Holdout v1 | v3 | 0.7500 | 0 | 5 |
| Holdout v2 | v4 | 0.1000 | 0 | **18** |
| 开发回归 34 案 | v6 | 0.9630 | 0 | 1 |
| Holdout v3（晋升） | v6 | **1.0000** | 0 | 0 |

v1 的主导失败是 **availability（11 次超时/HTTP 500）**，而 v4 是 **format（18 次）**。
两者是不同轴上的问题；v1→v3 的 names-only 契约修复针对的是内容与格式，不能解释 v1 的
超时，也不应把 v1 的低解析率整体归因于 Prompt。

### 同配置波动及其对晋升结论的影响

两次 v3 run 使用**同一 Prompt、同一 34 案开发集**，相隔约 5.5 分钟：
`20260804T032632Z-49aa87a206` 解析率 `0.9630`，`20260804T033209Z-b7e39be09d` 为 `0.7407`。
同配置解析率跨度 **0.2222**，无任何代码或 Prompt 变化。

这对晋升叙事有直接影响，必须披露：v6 Holdout v3 解析率 `1.0` 与 v3 Holdout v1 的 `0.75`
相差 `0.25`，**仅略大于实测的同配置波动 0.2222**。两者虽用不同 Holdout 集合、不构成严格
同配置对比，但该波动量级说明**单看解析率不足以确立 v6 优于 v3**。v6 晋升的实质依据应主要
落在内容质量轴（项目内人审 Grounding/Overall `0.95` vs `0.80`、事实门 `1.0`、注入抵抗 `1.0`），
而解析率的改善不能排除 Provider 波动贡献。v4 的 `0.10` 远超该波动范围，其"不晋升"结论不受影响。

反方向的证据也应同时记录：v6 在同一 34 案开发集上的两次 run（`20260804T080952Z-f8ecb44540`
与 `20260804T094026Z-ec55d5cd1d`）解析率均为 `0.9630`，**同配置跨度 `0.0`**。这提示 v6 相对 v3
不仅更高、也更稳定，但 `n=2` 且两次取值完全相同也可能是巧合，因此只作为初步信号，
不作为稳定性结论。要支撑"v6 更稳定"需要更多同配置重复运行。

### 统一 trace 与节点归因

Golden 路径此前完全没有节点级可观测性（只有受控链 `workflow_v2` 有 `node_timeline`）。
现在 `workflow.py` 的五个节点统一由 `_traced_node()` 包裹，产出与受控链**同一 span 结构**
（`node` / `timestamp_utc` / `duration_ms` / `status` / `state_change`），且 `state_change`
取自闭合词表，trace 消费方不需要解析自由文本。节点抛异常时先记 `status="failed"` 的 span
再向上传播，因此失败运行同样有 trace。

`run_investigation_traced()` 返回 `(报告, trace)`；`run_investigation()` 签名保持不变，
所以 API 响应模型不会被运维用的 span 撑大。Golden 每案 trace 写入与 summary 同目录的
`<output>_traces.jsonl`（summary 已有 56–88 KB，span 不再往里塞）。

首个真实 run 的 34 条 trace 显示延迟几乎完全来自外部调用，例如
`agent-low-evidence-03` 总耗时 `9909.9 ms`、其中 `annotate` 节点占 `9908.9 ms`。
这使"延迟由 Provider 还是本地模板造成"第一次可以按节点归因，而不是只看整案耗时。

未闭合部分：受控链与 Golden 路径**尚未共用同一个 trace 标识**（Golden 使用
`golden-<case_id>`，受控链使用 `thread_id`），因此还不能把同一告警在两条路径上的执行拼成
一条链。这属于后续工作，本次不宣称已实现端到端分布式追踪。

```powershell
  --output-cost-per-million-tokens-usd <价格>
```

事后计价对覆盖不完整的 run 只给下界：`billable_cost_is_lower_bound=true`，且
`wasted_cost_usd_from_recorded_tokens` 返回 `None` 而不是 `0.0`——因为失败调用的 token 从未
采集时，`0.0` 会被读成"没有浪费"，而事实是"浪费未被测量"。

边界：延迟为本机整案耗时（含确定性模板部分），不是在线服务 SLA；未配置合同价格时
全部成本字段保持 `None`；本节结论只覆盖本机已冻结 run，不构成 Provider SLA 或独立评测。

## 受控 Agent 工程验证

### 60 案回归与审计

60 案回归的 Case 通过率、工具选择准确率、参数合法率、事实一致率和恢复成功率均为 `1.0`。
持续检索失败会记录 `TimeoutError` 并回退确定性模板，状态仍停在
`draft_requires_human_review`。每案保存节点时间线；工具事件只记录工具名、参数名、输出键、
耗时、状态和错误码。

LangGraph checkpoint 与追加式 SQLite 审计库相互分离。审计表使用稳定 `event_id` 和
`INSERT OR IGNORE` 防止回放重复，不保存证据正文、特征值、图边或备注正文；Evidence Store
则保存完整 Evidence Package，必须使用受限文件权限和受控磁盘。SQLite 只是本地演示后端，
不等同于集中/WORM 审计、组织保留策略或生产访问控制。

### 审批幂等与多 worker

审批接口支持 `Idempotency-Key`：同键同正文返回幂等回放，同键不同正文或无键重复终态返回
`409`。单进程探针以 50 个线程、每线程 8 个并发同键审批发出 400 个请求，错误率 `0%`，
350 个为回放，审计库最终各有 50 条 review/finalize；周期 p50/p95/p99 为
`526.97/668.67/849.61 ms`。

两真实 Uvicorn worker + 四个分离的共享 SQLite 文件下，跨连接证据读取 `40/40` 为 `200`；
20 个线程共 160 个审批请求得到 20 次实际执行、140 次回放、0 错误，review/finalize 各
20 条，活动租约归零。该结论限于本机多进程，不代表跨主机 exactly-once 或生产 SLA。

### 租约续期与故障注入

线程租约使用 `owner_token`、默认每 `lease_seconds/3` 心跳续期和 fencing。续期失败或释放时
不再持有租约会抛 `LeaseLostError`，API 映射为可重试的 `503`；过期持有者不能误删接管者租约。
9 项回归覆盖持有 3 倍租约周期、崩溃后接管、owner token 被夺、非法参数和 API 映射。旧实现
“租约过期后两个 worker 同时进入临界区”的问题已实测复现并由这些用例锁定。

边界仍是单机多进程：跨主机数据库、网络分区和真实进程 `SIGKILL` 未验证；进程退出后依赖
租约自然过期，最坏停顿一个 `lease_seconds`。
