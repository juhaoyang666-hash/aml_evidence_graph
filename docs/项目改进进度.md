## 一、总体结论

当前已经形成可演示、可复现的 AML 风险排序与证据约束调查原型。投递前 P0、P1 工程项均已
完成；P2 为仅在目标岗位明确要求时开展的选做项，尚未开始。

项目最完整的技术主线是：

1. 对约 950 万笔公开合成交易构建严格 Point-in-Time 特征和历史交易图。
2. 使用规则、LR、LightGBM 和 GAT 完成交易级风险边排序，CatBoost 保留为历史对照。
3. 采用固定时间外切分、PR-AUC、固定告警预算、Bootstrap、漂移和资源指标评估。
4. 将账户、资金路径和案件视图作为交易分数的后评分聚合，不构造账户监督标签。
5. 将 LLM/Agent 限制在证据包、白名单工具、事实校验和人工审批范围内，不参与风险打分。

当前公开主线已按本机完整证据更新：LightGBM FE v2 为主线表格模型（test PR-AUC
`0.90141`）；`GAT + event_time_novelty` 为主线图排序器（`0.97140`）；LightGBM FE v2
+ 本机 GAT v1 replay 为 OOF 融合（`0.95606`）。融合用于展示 expanding-time OOF、
概率校准和阈值工程，不是性能冠军，且不能描述成包含时点新颖性 GAT。

时点新颖性通过双 seed、配对 validation 门禁和唯一一次冻结 test；相对本机 v1 replay
点差 `+0.01922`，200 次配对 Bootstrap 95% CI `[+0.01152, +0.02798]`。提升主要来自
新端点和低度交易，部分已见账户及 Smurfing 切片退化，因此对外结论严格限定为公开合成
SAML-D 上的时间外实验，不外推为真实业务收益。

|---|---:|---|

重训版结果不同，说明结论对 checkpoint / 训练波动敏感；当前作为更强的

GAT v1 本地重训 / 跨版本融合为 `0.95218 / 0.95048`。后者相对 GAT v1 本地重训

### 4.5 租约续期与故障注入（已关闭）

原 `SQLiteThreadLockRegistry` 只在进入临界区时 claim 一次租约，不续期、不做持有校验，
因此单次请求一旦超过 `lease_seconds`，租约会被回收而持有者毫无察觉，**两个 worker 可同时
进入同一 `thread_id` 的临界区**。该缺陷已在旧实现上实测复现，不是理论推测。原设计依赖
“租约 10 分钟 > 单次工作流耗时”的口头约定，但完整融合评分 p95 已达 `34.85 s`，且该约定
无强制、无回归。

现已实现心跳续期（默认 `lease_seconds/3`）、基于 `owner_token` 的 fencing 校验、
`LeaseLostError` → HTTP `503` 映射，并顺带修复了 `_claim` / `_release` 的 SQLite 连接泄漏。
新增 `tests/api/test_thread_lease.py` 9 项故障注入回归（续期保活、崩溃接管、租约被夺、参数校验、
API 映射），当前全量测试 `163 passed`，`ruff check src tests scripts` 通过。

边界：仍为单机多进程结论。跨主机数据库、网络分区、真实 `SIGKILL` 未验证；进程被杀后靠租约
自然过期恢复，最坏停顿一个 `lease_seconds`。详见
[大模型调查系统.md](大模型调查系统.md) 的“租约续期与故障注入”。

### 4.14 事实门补上文字量级断言（已关闭）

4.13 造探针时发现的安全缺口：事实门只拦数字字面量与实体 token，
`"The withheld score sits in the top decile"` **零错误通过**。所有值对 Provider 都是 withheld，
因此任何量级断言都是编造，只是不带数字；v6 起的指令禁止了，但**指令不是强制**。

**先量数据再写规则。** 冻结 run 已提供带标签语料：v1 的 13 条被接受注释人审 grounding `0.0`，
v3/v6/v7/v8 的 157 条合规。直接封禁量级词会误拒约 15% 合规注释——合规注释同样用这些词，只是
用在**否定**里（"does not imply that these values are high, low"）。三个变体实测：

| 变体 | 命中违规 | 误拒合规 |
|---|---:|---:|
| 词级封禁 + 仅豁免名称 | 12/13 | 9/107（8%） |
| 词级封禁 + 豁免名称与注记 | 10/13 | 0/107 |
| **短语级豁免（最终）** | **10/13** | **0/157** |

豁免刻意做成**短语级而非词级**：注记里出现 "high risk" 不能因此放行 "the score is high"，否则
一条注入注记就能关掉整个门。

影响：157 条合规注释零误拒，v3/v6/v7/v8 已发布的 `external_fact_validation_pass_rate = 1.000`
不变；v1 那栏发布的 `0.867` 配人审 grounding `0.000` 正是缺口本身——13 条过了自动门却要靠人工
拦下，新规则拦下其中 10 条。未追改任何已发布数字。漏掉的 3 条不含量级词，断言的是 Typology
适用性，属另一条规则。新增 `tests/investigation/test_magnitude_gate.py` 18 项回归（假阳性用例
占一半），全量 `267 passed, 1 skipped`。

> 实现中自己埋过一个坑并靠测试发现：我一度把 `withheld` 放进否定线索表，结果
> "the **withheld** score sits in the top decile"——即触发整件事的那句话——被自己的豁免放行。
> 它读着像限定词，实际什么也没否定。

### 4.13 Holdout v5 与 Prompt v8（修好了目标缺陷，仍然未晋升）

预注册协议在提交 `0025fd8` 冻结、先提交再运行，24 案 / 20 外部调用唯一执行。**v8 未晋升，
默认 Prompt 仍为 v7。**

**它要修的东西修好了。** v6/v7 要求模型自己判断"什么算字段名"，而"controller tenure"读起来
就是普通英语。v8 只改这一条子句：改成**封闭词表**（只许用"withheld model values /
authorized source records / corroborating context / independent verification /
record completeness / retrieved typology hypotheses"等固定说法）加一条机械禁令（供给名称里
出现过的词一律不得使用）。系统指令与 v7 逐字节只差这一处。

| 指标 | v7 | v8 |
|---|---|---|
| 案件泄漏率（3 次） | 0.500 / 0.583 / 0.833 | 0.417 / 0.417 / 0.417 |
| 泄漏名字数（3 次） | 16 / 27 / 27 | **6 / 9 / 6** |

按 v4 的先例记为诚实负结果，并已作为第 7 个阶段写入公开证据。

> 单次运行曾让我误判：v7 首轮恰好是它最好的一轮，据此我一度认为 v8 "只是噪声"。3 次重复才
> 看清。开发集上单臂单次运行不足以判定 Prompt 优劣，这条教训本身值得记。

顺带发现一个**更严重且未修**的缺口，已用测试钉住：事实门只拦数字字面量和实体 token，不拦

### 4.11 截断失败的有界重试（机制已闭环）

350→500 只是降低频率而没有消除该失败模式，且它活在**已晋升的默认路径**上。现已允许客户端对
且仅对截断重试一次（更高 token 上限）；超时、HTTP 错误、传输失败和一般 JSON 非法一律不重试，
因为它们不携带"第二次该改什么"的信息，重试只会抬高表面成功率并掩盖 Provider 不稳定性。

**协议先于代码。** Holdout v1–v3 的 "no per-case retries" 针对的是评测者，不是被测系统自身
的行为；两者混用会让链内重试看起来违规。因此先冻结
[golden/llm_retry_policy_v1.json](../golden/llm_retry_policy_v1.json)：评测者重试仍然禁止且
v1–v3 结论一字不改；链内重试须运行前声明、最多 1 次、只由截断触发；**每案不再等于每次调用**，
案件数与调用数必须分别报告，两次尝试都进入计费与浪费统计。该策略只对 Holdout v4 及以后生效。

**v7 当时是候选。** 提高生成上限属于配置变更，按 v5 的先例必须新开版本号。
`ecnu-risk-evidence-v7.yaml` 的 `system_instructions` 与 v6 逐字节相同（由回归测试固定），
只多 `truncation_retry_max_tokens: 1000`；v6 文件哈希仍为 `59aeb8d2…`，与 Holdout v3 预注册值
一致。晋升走的是预注册 Holdout v4（见 4.12）：收窄到可用性轴的理由**写在协议里、跑之前**——
重试只在解码失败时触发、不可能改变已成功的调用，因此首次尝试的注释与 v3 已复核配置同分布，
内容证据承接；该论证省掉的是配对 v6 对照臂，而非内容复核本身。

真实缺陷是 27 次里 1 次，`n=1` 量不出东西，因此先用确定性桩 Provider 把截断率设定为固定值
（20 案中 4 案越界，零外部调用）：v6 基线解析 `0.8000`、v7 候选 `1.0000`，4 次截断全部恢复。
关键读数是**浪费的绝对金额没变**——重试不减少浪费，而是用 `26.9%` 的额外开销换回 4 份原本
失败的草稿。把它说成"修好了浪费"是错的。

随后用 `ecnu-max` 做了三个真实 run，得到一个**必须披露的负结果**：

| run | Prompt | 解析率 | 外部调用 | 截断重试 |
|---|---|---:|---:|---:|
| `20260804T094026Z-ec55d5cd1d` | v6 | `0.9630` | 27 | — |
| `20260805T025859Z-b22df241b7` | v7 | `1.0000` | 27 | **0** |
| `20260805T030152Z-d4442a83ef` | 强制上限 200 | `1.0000` | 12（6 案） | **6，全部恢复** |

v7 在 shipped 上限下**重试零触发**，因此 `1.0000` 相对 `0.9630` 的提升**不能归因于重试**：
v6 那次撞上限的 `agent-typo-17-cycle` 这次只用了 391 token。该点差远小于已记录的同配置波动
（v3 跨度 `0.2222`），属噪声。真正结论是**截断是完成长度的运行间波动而非案例固定属性**；
27 次真实调用最长完成 `462`，距 `500` 仅 38 token，尾部会周期性蹭上限。

既然自然截断等不到，就把上限降到 200 主动触发，得到重试路径唯一一次真实端到端验证：6 次真实
截断全部在第二次尝试恢复，6 份被恢复的注释全部通过事实门，token 覆盖 `1.0`，其中
`46.11%` 的 token 花在被丢弃的首次尝试上。降低上限是实验设置，`6/6` 不是现场截断率；三个 run
都是开发集回归，都不构成 v7 晋升。

连带修好一条同方向的低报路径：`usage` 为空既可能是"没有这次调用"也可能是"调用发生但未报
token"，两次尝试只有一次报 usage 时按"空即无调用"求和会把半张账单当整张账单。现由
`external_usage_complete` 显式阻断，缺 usage 的案件整体退出 billable 口径并拉低覆盖率。该
缺陷由回归测试先复现再修复。

新增 `tests/investigation/test_truncation_retry.py` 21 项回归、
`scripts/operations/diagnose_truncation_retry.py` 与
`scripts/reporting/publish_truncation_retry_evidence.py`（源 summary 含模型原文，公开件只输出
计数）；全量测试 `226 passed, 1 skipped`，`ruff check src tests scripts` 通过，发布门禁 8/8。
运维报告现覆盖 13 个 run 共 248 次外部调用，此前 11 个 run 的解析率、调用数与 50 次不可恢复
计数全部未变。详见 [大模型调查系统.md](大模型调查系统.md) 的"截断的有界重试"。
